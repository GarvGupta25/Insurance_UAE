# Marketplace Pivot v2 — Phase 3 report

Phase 3 adds both mandatory broker checkpoints to the existing broker workflow. No provider
workspace or matching/ranking flow from later phases was added.

## Enforcement locations

Checkpoint 1 continues to use the existing case recommendation approval written by
`backend/app/main.py::review_recommendation`. The marketplace transition is enforced in two places:

- API/transaction: `backend/app/marketplace_broker.py::send_to_providers` locks the assigned
  application and calls `checkpoint_one_approved` before changing `broker_approved` to
  `sent_to_providers` in the same transaction.
- Database: `supabase/migrations/202609190003_marketplace_checkpoints.sql` installs
  `marketplace_application_checkpoint_guard`, which rejects the transition without an approved
  recommendation `ReviewDecision` for the same case.

Checkpoint 2 is a separate `ReviewDecision` identified by `marketplace_application_id` and
`checkpoint='checkpoint_2'`:

- API/transaction: `approve_checkpoint_two` requires both `provider_accepted` application status
  and an accepted `provider_quotations` row before recording the second approval.
- Reusable binding guard: `require_binding_approval` rejects binding without both the accepted
  quotation and Checkpoint-2 record. Phase 5's provider Start Policy endpoint can call this function.
- Database: `marketplace_policy_checkpoint_guard` rejects policy inserts unless the application is
  at `broker_final_review`, its quotation is accepted, and its separate Checkpoint-2 approval exists.
  The application-status trigger applies the same protection to a direct transition to `bound`.

The PostgreSQL migration was applied to the local Supabase database. Transactional trigger probes
confirmed that an unapproved `sent_to_providers` update and an unapproved policy insert are both
rejected; all probe rows were rolled back.

## Broker workspace

`frontend/src/MarketplaceBrokerPanel.tsx` is mounted inside the existing `Broker.tsx`. It displays
all submitted quotations for the selected marketplace case side by side, including provider,
premium, key terms, status, and submission time. The same view shows both approvals with broker,
timestamp, action, note, and edits, and exposes the Checkpoint-2 approval action when appropriate.

The existing `broker_worklist` aggregation now appends Checkpoint-1, Checkpoint-2, and open provider
flag items before applying its existing oldest-first sort. Blocking marketplace items share the
highest urgency at equal age; no second queue was introduced.
