# First four build gates

This records the first four implementation gates from `PLAN.md` §19 against the integrated Helm build. These gates cover the source contracts, shared evaluator, immutable history and appeals, and intake through broker-approved policy creation. The remaining website, agent, voice, reporting and handoff work is outside this sign-off.

| Gate | Delivered behavior | Verification |
| --- | --- | --- |
| 1. Foundation and contracts | The unchanged challenge JSON is loaded as the fictional plan/profile/event source. Typed profile fields preserve the supplied applicant facts. Supabase migrations create the saved case, recommendation, policy and servicing structures. | Original source adapter tests pass. Local Supabase applied migrations `202609120001` through `202609130004` without resetting existing data. |
| 2. Ledger and shared evaluator | Claims, reimbursements and pre-authorisation forecasts share deterministic policy-term evaluation. Money is calculated in integer fils, while original fixture outputs remain in AED. Forecasts do not debit the ledger. | Domain boundary tests and the fixture tour pass. The tour checks the supplied order, amounts and final ledgers for all five applicants and 13 events. |
| 3. History, appeals and replay | Decisions and broker reviews append records. An evidence-backed overturn keeps the original denial and rebuilds downstream effective amounts. Appeals are limited to currently denied claims or reimbursements; a broker cannot overturn one without attached evidence. | Unit/API tests cover APP-1, APP-2, late claims, downstream revisions and invalid appeals. The live two-account Supabase smoke flow records a denial, broker overturn and corrected ledger. |
| 4. Intake, comparison and approval | A saved profile produces three indicative quotes, classification flags and an explained recommended plan. A selected supported plan becomes a prepared application; an assigned broker must approve or edit it before the member can confirm and create a demo policy. | All five supplied applicants receive their expected intake-only recommendation. Live member and broker accounts completed profile → quote → approval → policy → claim → sandbox receipt without direct policy edits. The local Helm landing page also rendered in a browser. |

Run the reference fixture tour from `backend/` with `uv run python -m scripts.fixture_tour`. Run the real local journey with `uv run python scripts/live_smoke.py` after starting Supabase, the API and the worker. The smoke script creates disposable synthetic accounts and assigns its broker through the local administrator database connection. It does not contact a real insurer or move money.

The four gates do not sign off the full eight-phase product. Further work includes the substantial broker/member workflow polish, unresolved-case routing, broader voice drafting and contextual answers, history-based fit depth, fixture presentation in the website, and complete acceptance/handoff checks. Local Groq speech and Razorpay test integrations were not exercised by these gates.
